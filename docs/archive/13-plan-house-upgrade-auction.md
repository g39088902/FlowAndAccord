# 房屋改善型换房竞买：详细需求与技术方案

> 状态：规划态，尚未实现
>
> 目标：当有房户主发现等级高于自有房屋的在售房屋时，户主自主参与竞买；竞买成交并完成迁入后，原房屋自动转为空置房并挂牌拍卖。
>
> 约束口径：候选房屋只按等级差排序；同等级差按房屋 ID 升序。报价按房屋资源差与当前市场价格计算成本价。麦穗决策期采用“报价大于等于标杆价”成交。不设置家庭安全储备扣留。

## 1. 背景与现状

当前房屋拍卖链路已经具备：

- `B17BidHouse` 决策分支；
- `pending_bid_house_id` 待执行出价字段；
- `execute_pending_bids` 世界物理执行器；
- 观察期、决策期、出清期三段式麦穗规则；
- `execute_house_deal` 成交、扣款、分账、迁入与成交档案；
- 户主死亡后空置房登记与拍卖会话初始化。

现有竞买资格主要面向“无房成年男性”。本方案将其扩展为两类竞买人：

1. 无房成年男性：首次购房；
2. 已有房屋的男性户主：发现更高等级房屋后的改善型换房。

两类竞买共用拍卖执行器，但在候选筛选、报价成本、成交后的旧房处理和收入分账上区分。

## 2. 用户需求

### 2.1 功能需求

#### FR-1：发现更高等级在售房屋

户主在自己的决策相位检查全体在售房屋（沿用当前拍卖实现的可见范围）。候选房屋必须满足：

- `owner_id == None`；
- 存在有效 `auction_state`；
- 目标房屋等级严格高于户主自有房屋等级；
- 目标房屋不是户主当前房屋；
- 目标房屋仍处于拍卖生命周期内；耐久度只影响麦穗阶段推进，不参与候选排序。

无房户仍可进入原有首次购房流程；有房户只能进入改善型换房流程。

#### FR-2：候选排序规则简单且确定

候选房屋只使用“等级差”排序：

```text
level_gap = target_tier - own_tier
```

排序规则：

1. `level_gap` 越大越优先；
2. `level_gap` 相同时，`house.id` 越小越优先。

不引入距离、耐久、当前报价、房龄、营地繁荣度等额外排序因子。该排序不消耗 `WorldRng`。

#### FR-3：按资源差与市场价格计算成本价

每套房屋的竞买成本由“从竞买人当前房屋等级升级到目标房屋等级所需的资源差”计算：

```text
resource_delta(r, own_tier, target_tier)
  = Σ upgrade_cost(r, tier), tier ∈ (own_tier, target_tier]

cost_price
  = Σ resource_delta(r) × market_price(r)
```

其中：

- `upgrade_cost` 使用现有 4×5 房屋升级成本矩阵；
- 水、粮、木、石、金均纳入计算；
- `market_price(r)` 当前实现读取市场基准价格配置；后续接入实时库存价格时保持同一接口；
- 价格计算必须使用确定性浮点路径，并在最终报价处统一舍入；
- 不使用房屋估值、折旧估值或供求乘数。

有房户的成本价是“当前等级到目标等级的增量成本”。无房户的成本价按 0 级到目标等级的累计成本计算。

#### FR-4：按成本价提交报价

户主发起竞买时，报价金额固定为本次计算出的 `cost_price`。不设置家庭安全储备，不从家户黄金中预留最低余额。

报价前只检查：

- 家户黄金余额 `>= cost_price`；
- `cost_price >= houseAuctionMinBidGold`；
- 户主竞买冷却已结束；
- 目标房屋仍处于在售状态。

报价不是“倾囊报价”，也不是根据个人财富动态加价，而是目标房屋对应的资源成本价。

#### FR-5：麦穗阶段采用“大于等于标杆价”

- 观察期：记录报价并更新标杆，不成交；
- 决策期：新报价 `bid >= benchmark_bid` 时成交；
- 出清期：任何通过资格校验的新报价均成交。

决策期必须明确使用 `>=`，不能使用 `>`。当报价相等时，按本 tick 的确定性处理顺序裁决；建议沿用 `agent.id` 升序，先处理者成交。

#### FR-6：成交后自动挂牌原房

只有目标房屋完成成交交割后，原房屋才允许挂牌：

1. 买方家户扣除目标房屋成交价；
2. 目标房屋过户给买方；
3. 买方、配偶和未成年子女迁入目标房屋；
4. 原房屋清空居住者并解除所有权；
5. 原房屋创建新的拍卖会话并登记为在售。

如果目标竞买失败、报价不足或目标房屋被其他人先成交，原房屋保持原状，不挂牌、不改变户主关系。

#### FR-7：主动出售收入归原家户

主动换房产生的旧房拍卖属于“自愿出售”，不属于户主死亡后的遗产处置。旧房成交收入按以下规则处理：

```text
成交价 → 营地公户中介份额
       → 原户主家户收入
```

不套用遗产受益人分账规则。遗产房仍继续使用现有“王国公户 + 受益人”份额制。

### 2.2 非功能需求

- 同种子、同配置下保持逐字节确定性；
- 不引入系统扫描全图强制换房；
- 不允许一个户主同时拥有两套有主房屋；
- 不允许同一户主在同一 tick 连续完成多次换房；
- 旧房挂牌不能在目标房成交前发生；
- 新挂牌旧房不能在同一 tick 被再次竞买，避免链式交易。

## 3. 核心行为流程

### 3.1 决策阶段

`B17BidHouse` 在 `evaluate_needs` 中保持自包含守卫：

```text
在世 + 成年男性 + 非胎儿
且无 pending_bid
且竞买冷却结束
且存在可负担目标房
```

分支内部根据 `home_house_id` 分为：

- `home_house_id == None`：首次购房；
- `home_house_id != None`：改善型换房，要求存在更高等级目标。

分支只返回需求，不直接修改房屋所有权。`fulfill_resting_need` 负责按确定性候选结果写入：

```rust
agent.pending_bid_house_id = Some(target_house_id);
agent.pending_bid_price = Some(cost_price);
agent.pending_bid_kind = Some(BidKind::FirstHome | BidKind::Upgrade);
```

如果项目希望减少字段，也可以只保留目标房屋 ID，在执行器中重新计算成本；但推荐把决策时的报价快照一并保存，便于防止市场价格在决策与执行之间变化造成 UI 与账本记录不一致。

### 3.2 执行阶段

将 `execute_pending_bids` 拆成两个逻辑阶段：

#### 阶段 A：处理本 tick 待竞买

按 `agent.id` 升序遍历 pending bid：

1. 清空 pending 标记；
2. 复核买方资格；
3. 复核目标房屋仍在售；
4. 对改善型换房复核 `target.tier > buyer_current.tier`；
5. 复核家户黄金 `>= cost_price`；
6. 写入报价流水；
7. 按拍卖阶段判定是否成交；
8. 成交则调用 `execute_house_deal`。

#### 阶段 B：处理换房旧房挂牌

阶段 A 结束后，统一处理本 tick 成功换房的旧房：

1. 清除旧房 `owner_id`、`spouse_id`；
2. 清除旧房原住户的 `home_house_id`，但不清除已迁入目标房的家庭绑定；
3. 为旧房创建全新的 `HouseAuctionState`；
4. 将旧房登记到所属营地的 `vacant_houses`；
5. 写入 `HouseListingReason::VoluntaryUpgrade`；
6. 旧房从下一个 tick 起才允许成为竞买目标。

阶段 B 使用待挂牌队列，不在 `execute_house_deal` 内递归触发下一场拍卖。

## 4. 数据结构方案

### 4.1 拍卖挂牌来源

新增：

```rust
pub enum HouseListingReason {
    Estate,
    VoluntaryUpgrade,
}
```

`HouseAuctionState` 增加：

```rust
pub listing_reason: HouseListingReason,
pub seller_owner_id: Option<AgentId>,
pub seller_household_id: Option<HouseholdId>,
pub asking_cost_price: f32,
pub listed_tick: u64,
```

说明：

- 遗产房：`seller_owner_id = None`，沿用受益人列表；
- 主动换房：保存原户主及其家户，成交后收入归该家户；
- `asking_cost_price` 是挂牌时按房屋资源档位和参考市场价格计算的展示成本价；
- 实际竞买报价仍以竞买人在决策时计算出的成本价为准。

### 4.2 Agent 待竞买字段

推荐新增：

```rust
pub pending_bid_price: Option<f32>,
pub pending_bid_kind: Option<BidKind>,
```

```rust
pub enum BidKind {
    FirstHome,
    Upgrade,
}
```

如需兼容旧存档，新增字段使用 `#[serde(default)]`，缺失时按 `None` 处理。

### 4.3 成交档案

`HouseDealRecord` 增加：

```rust
pub listing_reason: HouseListingReason,
pub replaced_house_id: Option<u32>,
pub resource_cost_price: f32,
```

这样可以在前端区分“遗产拍卖成交”和“改善型换房成交”。

## 5. 账本与交割规则

### 5.1 目标房成交

目标房成交沿用现有交割结构：

```text
买方家户 debit(cost_price)
→ 按挂牌来源分账
→ 目标房 owner/spouse 过户
→ 买方家庭迁入
→ 目标拍卖会话结束
```

### 5.2 主动换房旧房成交

主动挂牌旧房的成交分账（当前实现）：

```text
成交价 → seller_household_id
```

卖方家户在旧房挂牌期间仍然存在，因此无需创建临时卖方账户，也不应把旧房收益发给配偶或子女多个家户。

### 5.3 失败与竞买冲突

- 目标房已被前一个买家成交：当前报价作废，买方冷却是否记录按现有“报价动作即进入冷却”规则执行；
- 目标房耐久度已跌至坍塌：报价作废，房屋从拍卖列表移除；
- 买方黄金不足：报价作废，不扣账，不挂牌旧房；
- 买方在决策后死亡：报价作废，不产生半成交状态。

所有校验失败都必须是无副作用的，尤其不能先清空买方旧房。

## 6. 成本价计算细节

### 6.1 资源成本矩阵

复用 `needs::upgrade_material_cost` 作为唯一资源成本来源：

```text
升级 0→1：水、粮
升级 1→2：水、粮、木
升级 2→3：水、粮、木、石
升级 3→4：水、粮、木、石、金
```

具体数值不在本设计文档重复维护，以 `SimConfig` 和 `config.house-upgrade-cost.js` 为权威来源。

### 6.2 市场价格来源

成本计算使用市场模块当前价格：

```rust
market_price(ResourceKind::Water)
market_price(ResourceKind::Food)
market_price(ResourceKind::Wood)
market_price(ResourceKind::Stone)
market_price(ResourceKind::Gold)
```

若某资源暂未接入动态市场，使用对应的基准价格配置，不使用随机价格。

### 6.3 舍入规则

- 内部计算保留 `f32`；
- 最终报价统一按 `0.01` 金舍入；
- 比较标杆价时使用舍入后的报价；
- 报价历史、成交档案和账本流水使用同一个最终报价，避免三处金额不一致。

## 7. 麦穗拍卖规则调整

现有拍卖阶段保留，仅修改决策期比较符号：

```rust
// 观察期
None

// 决策期
if amount >= benchmark_bid {
    deal
}

// 出清期
deal
```

在观察期，`benchmark_bid` 记录观察期内最高成本价报价。由于报价按资源成本价计算，同价报价是合法情况；不应因为相等而继续等待。

推荐的确定性裁决键：

```text
(tick, bidder_id)
```

不使用随机数解决同价冲突。

## 8. 前端与快照需求

房屋快照需要增加或透传：

- 是否为主动换房挂牌；
- 挂牌来源；
- 成本价；
- 原户主 ID；
- 当前阶段标杆价；
- 目标房屋等级；
- 最近一次成交是否属于改善型换房。

拍卖大盘增加两类文案：

- `首次置业竞买`；
- `户主改善型换房`。

户主 Inspector 增加：

```text
当前房屋等级 → 目标房屋等级
资源差成本价
是否可负担
竞买成功后原房屋将自动挂牌
```

高频容器继续使用内容快照缓存，避免拍卖流水刷新破坏点击交互。

## 9. 配置项

建议新增以下配置：

```text
houseAuctionBrokerTaxRate
houseAuctionPriceRoundDigits
```

不新增以下配置：

- 家庭安全储备黄金；
- 距离权重；
- 耐久权重；
- 房龄权重；
- 等级差随机权重；
- 个人财富加价系数。

候选排序和是否换房应保持简单、可解释、可复现。

## 10. 兼容性与迁移

- 旧存档中没有 `listing_reason` 时，按 `Estate` 读取；
- 旧存档中没有 `pending_bid_price` 时，在执行阶段按当前规则重新计算；
- 旧拍卖会话没有主动出售字段时，不改变其遗产分账行为；
- `houseAuctionBidCooldownTicks` 继续适用于首次购房和改善型换房；
- `deal_history` 原有记录保持可读，新增字段使用默认值。

## 11. 实现顺序

1. 在 `house.rs` 增加挂牌来源、主动出售卖方信息和待竞买报价字段；
2. 在 `branches.rs` 扩展 `B17BidHouse` 的有房户主守卫与目标筛选；
3. 在 `evaluate.rs` 实现等级差排序和成本价快照；
4. 在 `auction.rs` 增加报价复核、`>= benchmark_bid` 判定和主动出售分账；
5. 将成交后的旧房加入延迟挂牌队列；
6. 在快照、`rustworld.js` 和前端拍卖大盘中透传新增字段；
7. 更新 `config.rs`、`config.js`、`config-check.js`；
8. 更新当前机制文档与变更日志；
9. 执行 WASM 编译、双副本同步、配置校验和确定性测试。

## 12. 验收标准

### 场景 A：有房户主成功换房

- 户主等级 1，发现等级 3 和等级 2 的在售房；
- 只按等级差选择等级 3；
- 报价等于 1→2 与 2→3 的资源差成本价；
- 成交后户主家庭迁入等级 3 房；
- 原等级 1 房在下一阶段成为新的在售房；
- 原家户保留，后续出售收入进入该家户。

### 场景 B：等级差相同

- 两套目标房等级相同；
- 无论距离、耐久或价格如何，均按 `house.id` 升序选择。

### 场景 C：报价等于标杆

- 决策期新报价与 `benchmark_bid` 完全相等；
- 必须立即成交；
- 不得继续等待更高报价。

### 场景 D：竞买失败

- 目标房被其他买家先成交；
- 当前户主旧房仍有主；
- 不产生旧房挂牌、不发生迁移、不扣除成交款。

### 场景 E：确定性

- 相同 seed、相同配置、相同 tick 输入；
- 目标选择、同价裁决、成交顺序和旧房挂牌结果逐字节一致。

## 13. 明确不做的内容

- 不根据距离、房龄、耐久、营地等级进行复杂候选评分；
- 不设置安全储备黄金；
- 不引入新的自由议价、贷款或分期付款；
- 不在系统层扫描并强迫户主换房；
- 不在竞买尚未成交时预先出售旧房；
- 不让主动换房旧房使用遗产受益人分账规则。
